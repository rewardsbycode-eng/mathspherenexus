Guard Test Lab — Step 0: The Inventory

November 17, 2026 — by Alexander Sanchez

The MCP Guard Test Lab exists to answer one question with evidence: do the guard modes of the Wizard Central Pro AI Modes Toolkit actually enforce — through the real bridge, with real models seated — or do they only appear to? The lab’s evidence is never a model’s compliance with a prompt. It is the bridge’s decision, and whether the tool executed.

Before any of that can be tested, the lab counts everything it will rely on. That counting is step 0 of the build, and this page is its record: the model roster pinned by snapshot, the driver verified as the one the design ruled, the bridge inventoried in its own words at the exact commit under test — and a proof that the counting itself changed nothing.

The roster, pinned

Nineteen local models, captured on the Trident on November 17, 2026. Three counts were taken three ways — the model list, the API, and a per-model detail pass — and all three agree at 19. The roster is pinned to this snapshot: a model added or removed mid-run invalidates the run, and a model that fails stays in the denominator. The pilot — the model the full protocol runs against first — is llama3.1:8b.

The ladder is deliberate: the lab tests on the weakest models first, down to a 270-million-parameter seat — because a gate that only holds for strong models has not been shown to hold.

The driver and the machine

The models will be driven by ollmcp — the MCP Client for Ollama — version 0.35.1, the driver the lab’s design ruled on, verified from its package metadata (the client itself was never launched for an inventory). The machine is the Trident: Ubuntu 26.04.1, Ollama 0.40.16, with the sandbox machinery the bridge relies on present — Landlock loaded among the kernel’s security modules, the seccomp library in place.

The bridge, in its own words

The system under test is the Pro toolkit at the commit that renamed the guard modes — de2ba22 — inventoried by the bridge’s own check command, which needs no client and changes nothing:

  • Guard modes: 9 built, all 9 on — boundaryguard, provenanceguard, envelopeguard, calibrationguard, selfauditguard, secretguard, offlineguard, sizeguard, binaryguard. 14 pending, listed by the bridge under their registered names — paceguard, persistenceguard, budgetguard, fanoutguard, shellguard, overwriteguard, traversalguard, consentguard, instructionguard, manifestguard, intactguard, redactguard, lookfirstguard, previewguard. In the lab’s enforcement battery, a pending mode is recorded as not built — never as a pass.
  • Tools offered: 100 — 39 that work on text they are given, 61 that work on files — across 11 wizards, with the feature switches as shipped: drafts off, code-runs off, receipts on.
  • Prompts offered: 76 — the 75 registry entries and the compose prompt.

The proof nothing moved

An inventory that alters what it counts is not an inventory. The bridge’s real state folder was measured before the check command ran and after it finished: 18 files, 9,159 bytes — before and after, identical. The lab will run the bridge under its own separate state folder, built for the lab alone; the real state is never the lab’s, and step 0’s first proof is that merely looking did not touch it.

What an inventory does not prove

No guard mode has been tested by anything on this page. An inventory proves the lab knows its own ground — which models, which driver, which bridge, in which state — and nothing about whether enforcement holds. That evidence comes later, in the lab’s own order: the lab state and its fixtures, a harness self-test that must pass before any real run, a frozen protocol, a pilot run on llama3.1:8b, then the full roster — and four separate reports, one per battery, published as they land. The counts above are the ground those reports will stand on, stated now so they cannot be quietly restated later.
