Wizard Central Pro AI Modes Toolkit — README

The README as published in the project's repository

🧙 wizard-central-pro-AI-modes-toolkit

A toolkit of command-line wizards that a person, or a language model on the same machine, can run, with a gate in front of everything a model may touch. What is in it, counted from the code:

  • 39 command-line wizards that run (wizards/), with 486 commands between them. Each is a separate program; most need nothing beyond Python (see What you need).
  • An MCP bridge (mcp/server.py) that lets a model on this machine use 107 of those commands as tools, but only what a person switched on, inside folders a person granted, checked by 9 guard modes, run behind a sandbox wall, and written to a receipts log.
  • 75 AI modes: named prompt texts that compose() combines into one system prompt with a SHA-256 fingerprint. The text is reproducible; what a mode does to a model's answers is not measured.
  • The wizard roster: 110 tool-style wizards in 25 categories, kept as registry data (name, category, description, a function schema). 39 of them have code here; the other 71 are descriptions only and cannot be run.

Everything here is checked by tests, and nothing is meant to be claimed that a test does not prove. Sections marked generated are written by python3 scripts/gen_readme.py from the code; tests/test_readme_gen.py fails when they are out of date, or when the code needs something they do not mention.

Before you share this repository: the ported wizards' code is private, copied from the owner's wizard_central (wizards/PORTING.md).

🚀 Getting started

From a fresh Linux machine (Debian, Ubuntu or Chromebook Linux):

sudo apt-get update
  sudo apt-get install -y git python3 python3-venv
  git clone https://github.com/rewardsbycode-eng/wiz-central-pro-AI-modes-toolkit.git
  cd wiz-central-pro-AI-modes-toolkit
  python3 --version                     # must be 3.12 or newer
  python3 -m venv .venv                 # .venv is in .gitignore
  . .venv/bin/activate                  # again in every new terminal

The repository is private: cloning it needs a GitHub account the owner has added as a collaborator.

Then only what you will use (see What you need):

pip install mcp py_landlock pyseccomp      # the MCP bridge and its sandbox wall
  pip install pyfiglet rich click            # bannerwiz and calendarwiz; the screens of examwiz and godfatherwiz
  pip install pytest sqlalchemy PyYAML       # only for supremewiz test, sqlwiz's database commands, privacywiz

Run everything from the repository root. A first check, in a few seconds each:

python3 tests/wizard_validation.py   # registry checks
  python3 tests/test_compose.py        # composer, fingerprints, cross-process reproducibility
  python3 tests/test_ported.py         # every ported wizard runs through the registry
  python3 wizards/helpwiz/bin/helpwiz list   # the wizards, from the registry

The full test loop runs every test file. On the owner's Chromebook a full loop took 26.5 minutes (2026-10-27); from the second loop on, it prints its own estimate from your machine's history:

python3 scripts/loop.py              # must end: LOOP GREEN (full)

For a green loop, install click, rich, py_landlock and pyseccomp first, and mcp for the loop to test the bridge. Measured in a virtual environment with no packages (2026-10-27): without click six test files fail, because calendarwiz crashes; without py_landlock, tests/test_sandbox.py fails (one test does not skip as the others do; not fixed yet); without mcp the bridge's tests say SKIP and the loop can still end green, so a green loop without mcp says nothing about the bridge. Without pyfiglet, bannerwiz's drawing tests say SKIP. What each result means is in docs/TESTING.md.

Compose modes into a system prompt

import sys
  sys.path.insert(0, "src")

  from engine.compose import compose

  result = compose(
      ["privacywiz", "stepwiz", "apijsonwiz"],
      user_query="Summarize this support ticket.",
  )

  print(result.system_prompt)   # one prompt, modes ordered by priority
  print(result.fingerprint)     # SHA-256 of that prompt
  print(result.modes)           # the modes in the order they appear in the prompt
  messages = result.as_messages()   # [{"role": "system", ...}, {"role": "user", ...}]

compose() builds the prompt; it does not call a model. You send it with your own chat call.

Higher-priority categories come first, and the prompt tells the model that the mode listed first wins any conflict:

Category Priority
Governance & Safety Guardrails 105
Governance & Safety 100
Reasoning Modes 80
Domain Expertise 60
Specialized AI 50
Output Styles 40
Data & Integration 30
Performance & Scale 10

What is reproducible. The same modes, the same prompt text and the same format version always produce a byte-identical system prompt, whatever order the handles are given in. The tests check this across separate Python processes with different hash seeds, and the saved fingerprints in tests/golden/ make any accidental edit to a mode fail a test.

What is not. This says nothing about what a language model does with the prompt. Model output can vary between runs, and a prompt can steer a model but not force it. Priority order is guidance to the model, not enforcement. No test measures whether a mode changes a model's answers.

Run a ported wizard

From the shell, each wizard is its own program: python3 wizards/<name>/bin/<name> --help. From Python:

from engine.ported import run

  r = run("@gitwiz", ["find", "commit"])   # a subprocess; returns CompletedProcess
  print(r.returncode, r.stdout)

Only the wizards in the PORTED table in src/engine/ported.py can be run this way (the list is under The wizards below). A command a wizard marks person-only is refused through the registry: a write needs a human at a terminal. @writewiz runs everything except its consent commands (commit, rollback, discard, purge-old, unprotect). python3 tests/test_ported.py checks them. Every command of every wizard is in docs/COMMANDS.md.

Export the tool wizards

from engine.wiz_modes_registry import (
      get_full_wiz_specs, export_llm_tools,
  )

  specs = get_full_wiz_specs()        # every spec, keyed by handle ("@debugwiz")
  tools = export_llm_tools()          # the 110 roster tools; AI modes are not included
  some_category = next(iter(specs.values())).category
  tools = export_llm_tools(categories=[some_category])   # a smaller list

Most of these schemas have no code behind them. The export covers the whole roster, and only the wizards in the PORTED table can run. To give a model only tools that work, use the MCP bridge, which offers only listed commands of ported wizards.

AI modes are instructions, not functions, so the default export leaves them out (include_ai_modes=True adds them). They are registered with deterministic=False, because model output is not deterministic.

Renamed modes. Five modes originally shared a handle with a roster tool wizard, so they were renamed with the same meaning: @chainwiz is now @stepwiz, @legwiz is now @lawwiz, @cachewiz is now @memowiz, @graphqlwiz is now @gqlwiz, @debugwiz is now @rootcausewiz. All 75 modes are registered.

The MCP bridge

mcp/server.py lets an MCP client use the AI modes as prompts and the ported wizards as tools, on this machine (ollmcp is the client verified end to end so far). It needs pip install mcp (version 2), and the wall needs py_landlock and pyseccomp on Linux. @mcpwiz is its settings panel: python3 wizards/mcpwiz/bin/mcpwiz status; python3 mcp/server.py --check says what is installed and what is switched on.

What the tests prove (tests/test_mcp_server.py, tests/test_mcpwiz.py, tests/test_guardrails.py, tests/test_sandbox.py):

  • Nothing is open by default. Only the receipts log and the 9 guard modes are on. The bridge, prompts, tools and each single tool are switched on by a person (asked twice at a terminal, or --yes in a script they run); a switch is read on every call, and mcpwiz panic turns everything off and removes every grant at once.
  • Only listed commands are tools. A wizard is offered only through its own wizards/<name>/mcp.json; 12 wizards ship one. A command of class never, or one the registry marks person-only, is never offered or run.
  • Paths need a grant. Every path a tool is given must lie inside a folder a person granted, for 1 minute to 33 days (mcpwiz grant, asked twice), at most 20 grants at a time; links and .. are resolved first. A missing or expired grant is a refusal, and the refusal is receipted.
  • Guard modes check each call before it runs: 9 built of 23 planned. Only a person at a terminal can turn one off.
  • Each call runs behind a wall: no input, an empty working folder, a throw-away HOME, a short environment, a time limit (at most 600 seconds), output cut at 64 KB. Landlock lets it read the toolkit's code and write only inside the granted folders and its throw-away HOME; seccomp denies socket, connect, io_uring_setup and ptrace. If the wall cannot be built and proven, the call does not run.
  • Every call, grant and refusal is written to a hash-chained receipts log (~/.mcp-wizard/receipts.log). The chain has no key: it shows an edit in the middle; it does not stop someone who can rewrite the whole file.

What the bridge does not cover: a model that has its own shell, outside the server, is outside the gate. The godfatherwiz REPL's model does not go through the bridge either; it is limited to a fixed list of look-only wizards (see Status), and moving it behind the gate is planned (see Coming).

✏️ Changing a mode

  1. Edit its text in src/engine/ai_modes_prompts.py.
  2. python3 scripts/gen_modes_doc.py
  3. python3 tests/test_compose.py --update-golden
  4. python3 scripts/loop.py, then commit.

If you skip step 2 or 3, a test fails. That is intentional.

🔄 When the code changes

python3 scripts/gen_readme.py rewrites this README's generated sections; --check only says which are out of date. The loop does not rewrite files while it tests them: it goes red, names the command, and you run it and look at the diff. The data the generator cannot read from the code (each status row's state, the programs, the placeholders under Coming, a line for each docs page) is at the top of scripts/gen_readme.py, and the test fails when that data no longer matches the code.
