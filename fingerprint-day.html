Is my toolkit the real one?

November 16, 2026 — by Alexander Sanchez

This morning began with the record, not with new invention. The founder had the full job lists for the fleet’s last two wizards — bonuswizard, number 40, the witness, and keepwizard, number 41, the keeper — compiled from the project’s own saved history, every item with its source and its date, nothing filled in. Reading keepwizard’s list brought an open question back to the table. It had been open since October 20: how the keeper’s integrity check will actually work. Today it was answered, reviewed, and stamped.

The check answers the plainest question a user can ask: is my toolkit the real one? It matters here more than most places. Wizard Central’s guard modes are code, and edited guard code is no guards — a toolkit that cannot tell whether its own files are the release’s files cannot promise anything about the rest.

The design, as stamped. A fingerprint list is made once, at release, from the exact packaged download — after the package itself has been validated, never from a user’s installed copy, so nobody can be talked into blessing an altered toolkit by simply regenerating its list. The list never includes itself. Its fingerprint is published in two independent places, and the user confirms the match by eye before the first run; if the two publications ever disagree, verification stops. The check itself is exact membership: every file the release should contain, present and matching — and nothing in the tree that should not be there. A toolkit that notices changed files but waves through added ones has not established the thing it claims to establish. And every failure is a named failure — anchor missing, anchor malformed, lists in conflict, tree not matching — never a quiet pass.

The hard question got asked, and the design answers it in its own words. Who checks the checker? A checker modified to always say “all good” would defeat the whole arrangement, so the design does not pretend otherwise. It keeps three claims separate — the list is genuine, the tree matches the list, and the code reporting both is trustworthy — and it builds the third on a cross-check: two checkers in different seats, each verifying the other’s files against the published fingerprint, under assumptions the design states out loud. What even that cannot prove is printed in the design too. This is not a root of trust against a hostile machine, and it does not call itself one.

The review path is part of the record. One of the house’s collaborators, CG, read the design in three passes, and each pass found a seam the pass before had missed — the last one in the house’s own draft wording, which claimed more than the construction guarantees and was tightened before the stamp. The founder’s ruling this morning made the corrected design the design of record.

Decided is not built, and this entry does not blur the two: the check does not exist yet. It will be built with keepwizard, in its ruled place in the order of work — after the guard sweep and bonuswizard — and the one implementation defect already known, a draft that reports unexpected files instead of failing on them, is on the books to be corrected and tested when that build comes.

Why write it in the diary before a line of it is built? The founder’s observation, after a month of keeping this diary: in this house, the things that get written down plainly are the things that get built. The diary is where the design stands in the open, dated, where the work can be checked against it later. Today the fingerprint design stands there.

A command is what you type. The name is what the project is.

— Alexander
